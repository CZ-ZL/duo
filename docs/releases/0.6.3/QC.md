# Public repository acceptance

Acceptance is against the supported v0.6.3 product, not a claim of method
superiority or universal host support. Exact execution results are attached as
`VERIFICATION.json` on the tagged Release.

| Criterion | Implemented acceptance mechanism |
|---|---|
| Product is understandable | Concise bilingual README: purpose, start, supported work, result and limits |
| Installation is complete | Fixed archive, checksum, host manifest, read-only host check and free run |
| Compatibility is explicit | Linux/Node/DSH composition; metadata failures before preparation |
| Public task path works | Installed describe → plan → run → report acceptance |
| Core responsibilities are legible | Separate operation, evaluation, selection and final modules |
| References are navigable | Provider index and linked tool/API reference |
| Optional features do not crowd onboarding | Dedicated decision, shadow, model and troubleshooting guides |
| Simple is correctly scoped | Shared method pages and diagrams; study versions separately documented |
| Repository size is justified | Runtime contains only declared package files; tests/research stay outside |
| Retained scripts have owners | Checked role inventory and explicit verification consumers |
| Documentation stays valid | Local file/anchor checks and byte-bound historical exceptions |
| Bilingual instructions agree | Exact shell-block equality checks |
| Diagrams are valid and readable | Parser with negative control; separate visual review |
| Evidence is preserved | Frozen records and original snapshots remain byte-identical |
| Delivery is traceable | Exact-commit CI, same tested archive, checksum and download receipt |

No broad historical directory is ignored by QC. Original unavailable-input links
remain exact, byte-bound exceptions; they do not imply reproducibility from a
partial archive. Meta, private profiles, raw journals and unpublished research
inputs are outside publication scope.
